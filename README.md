# template-go-monolit

Go-монолит с HTTP API, PostgreSQL и миграциями Goose. Все команды ниже запускаются из корня репозитория.

## Назначение шаблона

Этот репозиторий — моя стартовая заготовка для других собственных проектов на Go. Его можно копировать для нового сервиса, переименовывать и развивать под свою предметную область, сохраняя готовую структуру приложения и инфраструктуру.

В шаблоне уже есть HTTP API на chi, PostgreSQL через pgxpool, SQL-миграции Goose, менеджер транзакций, ручной DI-контейнер с ленивой инициализацией, структурированные логи, graceful shutdown, WebSocket и окружение Docker Compose. Повторяющуюся настройку можно взять отсюда, а основное внимание уделить логике нового проекта.

Сущность `User` и сценарий `CreateAndDeleteUser` служат примером прохождения запроса через слои и выполнения транзакции. Для нового приложения их можно заменить своей логикой. Этот сценарий создаёт и удаляет пользователя в одной транзакции: он не является готовым CRUD пользователей. Авторизация, регистрация и управление правами в шаблоне не реализованы.

## Как использовать для нового проекта

### 1. Создать собственный репозиторий

Можно создать новый репозиторий из этого шаблона через GitHub, если для него включена функция **Use this template**, либо клонировать проект:

```bash
git clone https://github.com/Weit145/template-go-monolit.git my-service
cd my-service
```

При обычном клонировании сохраняется история исходного репозитория. Для работы со своим репозиторием поменяйте `origin` на его адрес:

```bash
git remote set-url origin https://github.com/your-name/my-service.git
```

`your-name/my-service` во всех примерах ниже — пример имени нового репозитория; замените его своим. При создании через GitHub Template клонируйте уже свой репозиторий, менять `origin` не требуется.

### 2. Переименовать Go-модуль и импорты

Для локальной разработки нужен Go версии 1.26.0 или совместимой более новой версии, указанной в `go.mod`, а также Task. Для запуска инфраструктуры нужны Docker и Docker Compose.

Задайте имя нового модуля:

```bash
go mod edit -module=github.com/your-name/my-service
```

Затем через поиск и замену в IDE замените в импортах всех `.go`-файлов:

```text
github.com/Weit145/template-go-monolit
→ github.com/your-name/my-service
```

Один `go mod edit` не меняет импорты в исходниках. После их замены выполните:

```bash
go mod tidy
task test
task app:build
```

Обновите название и описание в README и `docs/api/v1/swagger.yaml` под новый сервис. Отдельные внешние зависимости, например `github.com/Weit145/simple-log` в Dockerfile, не являются именем модуля шаблона: их переименовывать вместе с проектом не нужно.

### 3. Настроить окружение и запустить

Создайте локальный файл настроек:

```bash
cp .env.example .env
```

Настройте параметры в `.env`, затем запустите весь стек:

```bash
task build
```

Compose поднимет PostgreSQL, применит миграции и запустит приложение. После запуска проверьте `http://localhost:8080/_health` и откройте `http://localhost:8080/swagger/`. Файл `.env` исключён из Git; для новых настроек добавляйте описание и пример в `.env.example`.

Для запуска приложения непосредственно на хосте, с PostgreSQL в Docker:

```bash
docker compose up -d db
task migrate:up
DATABASE_URL='postgres://postgres:postgres@localhost:5432/postgres' go run ./cmd/app
```

В примере используются стандартные имя БД, пользователь и пароль. Если вы их поменяли, согласуйте `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, строку `DATABASE_URL` для приложения и `PG_DSN` для задач миграций. Из контейнера адрес PostgreSQL — `db:5432`, с хоста — `localhost:5432`. Приложение при `go run` не читает `.env` автоматически.

Если запускаете несколько проектов одновременно, задайте им разные опубликованные порты в `docker-compose.yml`. Сейчас там фиксированные привязки `8080:8080` и `5432:5432`; смена только `HTTP_ADDRESS` их не меняет. Для независимых данных проектов используйте разные Compose project names, например через `COMPOSE_PROJECT_NAME` в `.env`.

### 4. Добавить свою функциональность

Удобно брать существующий сценарий пользователей как образец и проходить те же слои:

1. Опишите сущность, её правила и ошибки в `internal/domain`.
2. Создайте изменение схемы командой `task migrate:create -- create_products`, заполните SQL для применения и отката, затем выполните `task migrate:up`.
3. Добавьте необходимые методы интерфейса репозитория в `internal/usecase/port` и реализацию SQL-запросов в `internal/repositories/storage/postgres`. Преобразование строк БД в доменные модели находится в `postgres/model`.
4. Реализуйте бизнес-сценарий в `internal/usecase`. Для нескольких операций в одной транзакции используйте `trManager.Do(ctx, ...)`, как в сценарии пользователей. События об успешном изменении публикуйте после коммита.
5. Добавьте DTO в `internal/transport/api/v1/dto`, обработчик в `internal/transport/api/v1/handler` и маршрут в `handler/router.go`. Дополните интерфейсы сервисов, которые использует обработчик.
6. Если появились новые зависимости, соедините их в `internal/app/di.go`. Для ресурса с `Close` или `Shutdown` зарегистрируйте закрытие через `d.closer.Add` сразу после успешного создания.
7. Обновите спецификацию `docs/api/v1/swagger.yaml`, добавьте проверки бизнес-сценария и выполните `task test` и `task app:build`.

После появления собственной функциональности демонстрационные сущности, маршруты, SQL и тесты можно заменить или удалить согласованно. Если миграции уже применялись к используемой БД, изменения схемы оформляйте новыми миграциями, а не переписыванием применённых файлов. Описание действующих демонстрационных API и WebSocket сохранено ниже.

## Архитектура

Запрос проходит через `internal/transport/api/v1` (роутер chi, middleware, обработчики и DTO), затем через `internal/usecase` к `internal/repositories/storage/postgres`. Бизнес-модели и ошибки находятся в `internal/domain`. Точка входа `cmd/app/main.go` загружает `internal/config`, создаёт подключение к БД и запускает HTTP-сервер.

| Каталог | Назначение |
| --- | --- |
| `cmd/app` | Запуск приложения и сборка зависимостей |
| `internal/app` | Инициализация приложения, ручной DI-контейнер и управление жизненным циклом |
| `internal/closer` | Закрытие ресурсов в обратном порядке регистрации |
| `internal/config` | Настройки из переменных окружения |
| `internal/logger` | Настройка slog, идентификатор запроса и контекст ошибок |
| `internal/domain` | Бизнес-модели и ошибки |
| `internal/domain/event` | Общая модель события с UUID отслеживаемого объекта, типом и данными |
| `internal/infrastructure/websocket` | WebSocket-клиент, JSON-сообщения и Hub, реализующие интерфейсы usecase |
| `internal/usecase` | Сценарии работы и интерфейс репозитория |
| `internal/repositories/storage/postgres` | Работа с PostgreSQL через pgxpool |
| `internal/transport/api/v1` | HTTP API версии v1 |
| `migrations` | SQL-миграции Goose |
| `docs/api/v1` | Спецификация OpenAPI |

### Инициализация и завершение работы

В текущей реализации `cmd/app/main.go` создаёт контекст обработки `SIGINT` и `SIGTERM` и передаёт его в `app.New(ctx)` и `App.Run(ctx)`. Сборка приложения находится в `internal/app`: сначала загружается конфигурация, затем настраивается логгер и создаётся HTTP-сервер.

DI-контейнер в `internal/app/di.go` хранит зависимости и создаёт каждую при первом обращении к геттеру. Запрос обработчика собирает цепочку `Handler → Service → PostgreSQL / TrManager / Infrastructure`. Инициализация выполняется последовательно до запуска HTTP, поэтому геттеры не предназначены для конкурентного создания зависимостей во время обработки запросов. Контекст передаётся до подключения к БД: остановка приложения прерывает ожидание PostgreSQL.

При остановке HTTP-сервер прекращает принимать новые соединения и ждёт завершения текущих запросов в пределах настроенного таймаута. Затем закрывается WebSocket Hub и последним — пул PostgreSQL. Функции закрытия регистрируются при создании ресурсов и выполняются через `closer` в обратном порядке. Для завершения работы используются отдельные контексты с таймаутом, поскольку исходный контекст уже отменён. Ошибки инициализации и завершения возвращаются в `main`.

## Запуск через Docker

Нужны Docker, Docker Compose и [Task](https://taskfile.dev/docs/installation/). Файл `.env.example` показывает доступные настройки; при необходимости скопируйте его в `.env` и измените значения. Если `.env` отсутствует, Compose использует значения по умолчанию из `docker-compose.yml`.

```bash
task build
```

Команда собирает образы и запускает Compose в текущем терминале. Порядок запуска: PostgreSQL становится доступным → одноразовый контейнер `migrate` применяет миграции Goose → стартует `service`. Если миграция завершится с ошибкой, сервис не запустится. Уже применённые миграции Goose повторно не выполняет.

После первой сборки используйте `task up`. Для запуска в фоне: `docker compose up -d --build`. HTTP API доступен на `localhost:8080`, PostgreSQL — на `localhost:5432`. Внутри сети Compose приложение подключается к БД по имени `db`.

## Команды

| Команда | Что делает |
| --- | --- |
| `task build` | Собирает образы и запускает Compose |
| `task up` | Запускает Compose без принудительной пересборки |
| `task down` | Останавливает и удаляет контейнеры, сохраняя том БД |
| `task delete` | Останавливает Compose **и удаляет том БД со всеми данными** |
| `task app:build` | Собирает локальный бинарник `bin/app` |
| `task test` | Проверяет сборку пакетов и запускает тесты |
| `task goose:install` | Устанавливает Goose в `bin/goose`, если он ещё не установлен |
| `task migrate:up` | Применяет ожидающие миграции вручную |
| `task migrate:down` | Откатывает одну миграцию вручную |
| `task migrate:status` | Показывает состояние миграций |
| `task migrate:create -- имя` | Создаёт SQL-файл миграции |

Задачи `task migrate:*` запускаются на хосте и по умолчанию подключаются к `localhost:5432`. Для другого адреса укажите `PG_DSN`, например `PG_DSN='postgres://postgres:postgres@localhost:5432/postgres' task migrate:status`. При запуске через Compose вызывать `task migrate:up` отдельно не требуется.

Для запуска приложения без Docker сначала запустите PostgreSQL и примените миграции, затем выполните:

```bash
DATABASE_URL='postgres://postgres:postgres@localhost:5432/postgres' go run ./cmd/app
```

Приложение читает переменные окружения процесса; файл `.env` напрямую оно не загружает.

## API

| Метод и путь | Назначение |
| --- | --- |
| `GET /_health` | Проверка готовности приложения и БД |
| `POST /api/v1/users/create-and-delete` | Создание и удаление пользователя в одной транзакции; JSON-тело `{"name":"Alice"}` |
| `GET /swagger/` | Swagger UI |
| `GET /swagger/doc.yaml` | Спецификация OpenAPI |
| `GET /ws` | WebSocket-подключение |

Исходный документ API: [`docs/api/v1/swagger.yaml`](docs/api/v1/swagger.yaml).

Сценарий `CreateAndDeleteUser` возвращает `200 OK` и JSON `{"id":"<uuid>","name":"Alice","status":"created_and_deleted"}` после коммита. Пользователь в БД не сохраняется. Старый маршрут `POST /api/v1/users` удалён: обычное создание постоянного пользователя пока не реализовано.

### WebSocket

Подключение: `ws://localhost:8080/ws`. Поле `event_id` содержит UUID конкретного отслеживаемого объекта: пользователя, человека, устройства или другой сущности. Например, чтобы следить за человеком с UUID `6b173f43-916c-4d69-a52f-f5e57e68c804`, отправьте:

```json
{"type":"subscribe","event_id":"6b173f43-916c-4d69-a52f-f5e57e68c804"}
```

Для отписки отправьте тот же `event_id` с `"type":"unsubscribe"`. События получают только подписчики этого UUID. Постоянного общего канала пользователей нет.

Модель `event.Event` содержит `ID` отслеживаемого объекта, `Type` события и `Data`. Usecase публикует её через `EventPublisher`, а инфраструктурный WebSocket-клиент преобразует в JSON с полями `event_id`, `type` и `data`.

HTTP-обработчик принимает соединение и передаёт его в `Service.WebSocket` через интерфейс `port.WebSocketClient`. Usecase запускает чтение и запись, проверяет входящие команды `event.Command` и вызывает подписку или отписку через `port.EventHub`. Пустой UUID и неизвестный тип команды завершают сессию с ошибкой. Hub хранит клиентов через интерфейс и не зависит от HTTP transport или конкретной реализации клиента. Завершением HTTP-сервера и Hub управляет `cmd/app/main.go`.

После успешной транзакции `POST /api/v1/users/create-and-delete` публикуется событие `user.created_and_deleted` с ID полученного пользователя. Этот учебный сценарий создаёт и удаляет пользователя в одной транзакции; строка в БД не сохраняется. При ошибке транзакции событие не отправляется. Для получения события подписка должна существовать до публикации: UUID нового пользователя генерируется при создании, события без подписчиков не сохраняются и не воспроизводятся позже.

Один общий Hub хранит подключения и подписки. На подключение работают цикл чтения в usecase в горутине HTTP-обработчика и отдельная горутина записи. Очередь содержит до 32 сообщений; при переполнении новые сообщения для этого клиента пропускаются. Повторной доставки нет. При остановке приложения соединения закрываются и ожидается завершение сессий. Прикладной таймаут ограничивает ожидание сессий после закрытия соединений; библиотечный `CloseNow` имеет собственное ожидание завершения соединения.

## Конфигурация

Основные переменные: `HTTP_ADDRESS` (по умолчанию `0.0.0.0:8080`), `DATABASE_URL` (в Compose — `postgres://postgres:postgres@db:5432/postgres`), `LOG_LEVEL` и `HTTP_TRUSTED_PROXIES`. HTTP-таймауты задаются переменными `HTTP_READ_HEADER_TIMEOUT`, `HTTP_READ_TIMEOUT`, `HTTP_WRITE_TIMEOUT`, `HTTP_IDLE_TIMEOUT`, `HTTP_SHUTDOWN_TIMEOUT` в формате длительности Go, например `10s`.

Параметры пула PostgreSQL `MAX_CONNS`, `MIN_CONNS`, `MAX_CONN_LIFETIME`, `MAX_CONN_IDLE_TIME` необязательны. Если они не заданы, используются настройки pgxpool по умолчанию.

При старте пул PostgreSQL создаётся один раз. Готовность БД проверяется через `Ping`: до 10 попыток с таймаутом 2 секунды на попытку и паузой 2 секунды между неудачами. Отмена контекста останавливает проверку и ожидание; при окончательной ошибке пул закрывается.
